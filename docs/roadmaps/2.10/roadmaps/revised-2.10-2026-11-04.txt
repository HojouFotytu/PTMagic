I-3. CURRENT CONFIGURATION CONTRACT
-----------------------------------

The current format is settings.analyzer.json under:

   AnalyzerSettings.MarketAnalyzer
      StoreDataMaxHours
      IntervalMinutes
      ExcludeMainCurrency
      UseProfitTrailerEnabledPairs
      UseProfitTrailerAllowedUnderlyingTypes
      IncludedUnderlyingTypes
      MarketTrends[]

MarketTrend includes:

   Name, Platform, TrendMinutes, MaxMarkets, TrendThreshold,
   TrendCurrency, IgnoredMarkets, AllowedMarkets, DisplayGraph,
   DisplayOnMarketAnalyzerList, Metrics

"Metrics" is a comma-separated STRING of explicit supported names.
An omitted or blank Metrics string leaves a MarketTrend legacy-only.
The normalized engine does NOT implicitly enable PriceTrend.

Current recognized metric names (exact canonical spellings):

    PriceTrend             Global  normalized mean % return
    MedianPriceTrend       Global  median % return
    MeanMedianSpread       Global  mean minus median, percentage points
    Breadth               Global  % valid returns strictly greater than zero
    Dispersion            Global  population standard deviation of % returns
    Concentration         Global  Top10 return advantage in percentage points
    RelativeStrengthMarket Asset symbol return minus market median, pp
    RelativeStrengthBTC    Asset symbol return minus BTC return, pp

Special note: current Concentration is RETURN concentration, not volume share.
Top10 is ranked by complete trailing 24h quote volume. The result is the
arithmetic mean of those ten returns MINUS the arithmetic mean of returns
for the rest of the applicable global cross-section. It can be negative.
The planned Phase 1C VolumeConcentration is a different calculation and
requires a different metric name and unit.

PriceTrend is ambiguous unless the trigger configuration is explicit:

   MarketTrend.Metrics blank/omitted
       -> legacy PriceTrend only; normalized data not required.

   Trigger.Metric blank/omitted, regardless of MarketTrend.Metrics
       -> legacy PriceTrend trigger logic.

   Trigger.Metric = "PriceTrend", MarketTrend.Metrics blank
       -> legacy PriceTrend (compatibility behavior).

   Trigger.Metric = "PriceTrend", MarketTrend.Metrics includes PriceTrend
       -> normalized mean PriceTrend.

   Trigger.Metric = any other metric
       -> normalized metric only if explicitly enabled on that MarketTrend;
          unknown, disabled, missing, invalid or stale values FAIL CLOSED.

Normalized features are BinanceFutures-only as implemented. The resolver
checks exchange and metric scope/enablement. GlobalSetting cannot reference
an asset-only metric. SMS may use global values as shared market-wide gates
and asset values for the current market.

Comparison contract:

   MinChange <= metricValue < MaxChange

For explicit normalized SMS metrics, compare their value DIRECTLY.
Do not apply legacy MarketTrendRelation Relative or RelativeTrigger to them;
those relations only retain their historical semantics for legacy SMS paths.
This is essential to avoid double-subtracting relative strength.

Missing/invalid/stale is NOT zero. It must never be treated as a valid
zero-valued observation or used to satisfy a trigger inadvertently.

Testing example (valid only if the 4h MarketTrend enables Breadth):

    { "MarketTrendName":"4h", "Metric":"Breadth",
      "MinChange":60, "MaxChange":101 }

Never assume a nested conceptual "MarketAnalysis" configuration object from
the original roadmap is currently supported. Any new settings or metric names
must be added to the actual parser/model explicitly and documented.

I-4. PHASE 1B METRIC DEFINITIONS AND CURRENT INVARIANTS
-------------------------------------------------------

Normalized common return endpoint:
- 5-minute Binance candles; use a common exact latest CLOSED candle endpoint.
- Exact TrendMinutes lookback/reference timestamp, no nearest arbitrary candle.
- Configured return horizon must be compatible with the 5m base granularity.
- Insufficient history or missing reference/end candle => invalid feature.
- Current normalized return = (endClose/referenceClose - 1) * 100.
- A different legacy calculation may legitimately yield a different return.
- Each output records calculated time, source timestamp, sample count,
  validity/staleness and reason for invalidity.

Statistical definitions:
- Mean: ordinary arithmetic mean of valid common-endpoint returns.
- Median: median of valid common-endpoint returns.
- MeanMedianSpread: mean minus median in percentage POINTS.
- Breadth: count(valid returns > 0) / valid return count * 100.
  Zero returns are neutral, not positive. Denominator validity is explicit.
- Dispersion: population standard deviation of the valid % returns,
  not sample-corrected n-1 SD; requires at least two values.
- RS vs Market: asset return - global median return (percentage points).
- RS vs BTC: asset return - BTCUSDT return (percentage points).
- Concentration: top 10 by valid trailing 24h quote volume vs remaining
  global return universe, expressed as their mean-return difference in pp.

Cross-sectional validity must account for COVERAGE, not merely whether a
mathematical result can be computed from a subset of available assets.
See critical issue I-6. Do not silently loosen timestamp alignment to improve
coverage. Preserve valid/invalid metadata and repair ingestion/readiness.

I-6. IMPORTANT OPEN ISSUE: COLD-START CROSS-SECTION READINESS
--------------------------------------------------------------

Status: [ISSUE] — resolve BEFORE extending the calculation families.

Observed fact:
The first raid reported 756/756 kline refresh successes but only 259/1434
valid 4h asset metric values. The next raid refreshed 557 series and restored
1434/1434. The first raid's global metrics also used a smaller valid subset
than the nominal GlobalSymbols population.

Most likely direction of investigation:
A lengthy initial download crossed one or more 5m candle boundaries. The
series may have individually been current at their time of retrieval but
not all current at the common endpoint selected at evaluation time.
This is a hypothesis, NOT a proven root cause. Verify with timestamp-level
instrumentation before changing algorithms.

Correctness risk:
A market-wide value can be numerically valid for a subset yet misleading for
the configured Phase 0 market population. The first diagnostic global setting
was in fact selected on the initial raid, so partial coverage matters.

Mandatory hardening tasks:
[ ] Capture each series's latest closed-candle timestamp and contiguous
    lookback, grouped by exact expected common endpoint.
[ ] Make required endpoint an explicit frozen timestamp for the raid/analysis.
[ ] Investigate whether refreshed series finish at different closed candles.
[ ] Recheck/catch up series after the broad bootstrap when the candle boundary
    advances; use bounded requests, concurrency and rate limits.
[ ] Distinguish a NOT-YET-READY cross-section from sparse/newly listed assets.
[ ] Report count of expected, eligible, valid, invalid, stale and missing assets
    per metric and per exact universe, with invalid-reason categories.
[ ] Define explicit acceptable coverage (min sample AND coverage ratio),
    considering newly listed markets and intentional filtering; do not guess
    a threshold silently. Capture the denominator being used.
[ ] When readiness/coverage is insufficient, mark dependent metrics invalid
    and prevent normalized triggers using them from evaluating true.
[ ] Keep valid independent metrics available; legacy analysis must continue.
[ ] Test time-consuming startup crossing >=1 candle boundary, API throttling,
    dropped candles, old data, partial series, and fast normal start.
[ ] Re-run TestMode diagnostics and compare first/second/subsequent raids.

Do NOT fix by assuming missing asset returns are zero, silently changing
common-close alignment, enlarging StoreDataMaxHours without consent, or
rerouting old triggers to the normalized engine.

I-7. SMS OFF-TRIGGER BEHAVIOR: DOCUMENTED, NOT A NEW DEFECT
-----------------------------------------------------------

The BTC diagnostic deliberately gave the entry and off-trigger the same
RelativeStrengthBTC interval around zero. BTC RS versus itself is exactly
zero when valid; therefore BOTH conditions matched. Existing SMS processing
checked off-trigger, removed the activation record, then immediately checked
entry and reactivated the SMS in the same raid.

This resets activation time and can alter future HoursSinceTriggered logic,
but follows the existing state-machine ordering. No code change is warranted
solely because an intentionally contradictory diagnostic test did this.

Guidance:
- Use mutually exclusive thresholds (hysteresis) in real settings, e.g.
  entry Breadth >=60 versus exit Breadth <50.
- Preserve legacy SMS behavior unless same-raid off-trigger precedence is
  explicitly adopted as a separate breaking/behavioral decision.
- Add tests so an implementation change cannot accidentally alter legacy
  off-trigger and RefreshOffTriggers behavior.

9. Unsupported/missing feature references should fail closed with useful,
   rate-limited diagnostics; do not permit missing data to activate settings.
10. Older experimental fixed-horizon helper classes may remain compiled but

DETAILED FEATURE AND ARCHITECTURE DESIGN
========================================

Purpose
-------
This detailed section preserves the full technical scope of the original roadmap for expanding PTMagic's native analysis of Binance Futures market data. The current implementation/status and priority overrides in Part I take precedence when a historical passage below describes work as not yet present.

It intentionally excludes:
- Any external AI or LLM layer.
- Any AI-generated trading signals.
- Any AI API calls.
- Any architecture where an AI model directly changes ProfitTrailer settings.

The goal is to make PTMagic itself substantially more capable at measuring:
- Overall market direction.
- Market breadth.
- Cross-sectional dispersion.
- Volatility.
- Participation.
- Relative strength.
- Market concentration.
- Correlation / market cohesion.
- Futures positioning and leverage.
- Aggressive buy/sell flow.
- Liquidity and market stress.

The expanded analysis should remain deterministic, testable, cacheable, and usable by PTMagic's existing GlobalSettings and SingleMarketSettings mechanisms.

The broader design principle is:

    BINANCE RAW DATA
          |
          v
    NORMALIZED DATA STORE
          |
          v
    FEATURE CALCULATORS
          |
          +----------------------+
          |                      |
          v                      v
    PER-ASSET FEATURES      MARKET-WIDE FEATURES
          |                      |
          +-----------+----------+
                      |
                      v
               PTMAGIC ANALYZER
                      |
          +-----------+-----------+
          |                       |
          v                       v
    GLOBAL SETTINGS       SINGLE MARKET SETTINGS
          |                       |
          +-----------+-----------+
                      |
                      v
               PROFITTRAILER

PTMagic should collect and analyze better information; ProfitTrailer should remain responsible for its own actual entry/exit strategy execution.


======================================================================
1. CURRENT PTMAGIC ROLE
======================================================================

PTMagic remains primarily a market-state and configuration-management layer around ProfitTrailer. The LEGACY behavior described below is preserved; Phase 1 adds a parallel normalized analytical layer and explicit metric-based trigger routing.

Conceptually it:

1. Retrieves exchange/market data.
2. Calculates market trends over configured time windows.
3. Evaluates PTMagic GlobalSettings.
4. Evaluates per-market / SingleMarketSettings conditions.
5. Changes ProfitTrailer PAIRS, DCA, and INDICATORS settings.
6. Uploads those settings to ProfitTrailer.

The existing market-trend model is heavily based on price change over configured windows, generally applied across a selected set of markets.

Example existing conceptual measurements:

    Exchange2h
    Exchange4h
    Exchange8h
    Exchange12h
    Exchange24h

Typical PTMagic logic then interprets those measurements using threshold-based GlobalSettings such as:

    BULL
    BULLCON
    SIDEWAYS
    BEAR
    BEARCON
    BULLTRAP
    BOUNCE
    EXTRA

The purpose of this roadmap is NOT to replace this mechanism. The existing legacy threshold/preset system is live in the code and was not replaced by Phase 1B.

The purpose is to provide PTMagic with a much richer set of deterministic market measurements that GlobalSettings and SingleMarketSettings can use.


======================================================================
2. CORE ARCHITECTURAL PRINCIPLES [ACTIVE DESIGN CONSTRAINTS]
======================================================================

2.1 Keep exchange ingestion separate from analysis
--------------------------------------------------

The Binance client/networking layer should return raw exchange data.

Good examples:

    GetKlines()
    GetTicker()
    GetOpenInterest()
    GetOpenInterestHistory()
    GetFundingRate()
    GetLongShortRatio()
    GetTopTraderRatios()
    GetTakerBuySellVolume()
    GetBookTicker()
    GetOrderBook()

Bad examples:

    BinanceApi.GetMarketBreadth()
    BinanceApi.GetBullishness()
    BinanceApi.GetRelativeStrength()
    BinanceApi.GetCrowdingScore()

Breadth, volatility, relative strength, crowding, etc. are PTMagic analytical concepts and belong in PTMagic's analysis layer.


2.2 Build a reusable normalized market-data model
-------------------------------------------------

Raw data should be normalized into PTMagic-owned structures before analysis.

The feature engine should not be tightly coupled to Binance JSON response objects.

Conceptually:

    Binance response
        ->
    Binance mapper
        ->
    PTMagic market data objects
        ->
    feature calculators

This makes it possible to:
- Unit-test calculations without calling Binance.
- Change Binance endpoints without rewriting analysis.
- Potentially support other exchanges later.
- Cache data consistently.
- Reuse the same raw series for many metrics.


2.3 Calculate locally whenever possible
---------------------------------------

Do not add a new API endpoint simply because PTMagic needs a new metric.

Many useful measurements can be derived from the same price and quote-volume series:

    Breadth
    Dispersion
    Relative strength
    Concentration
    Correlation
    Volume expansion
    Volatility
    Return persistence

The first development phase should therefore maximize information extracted from basic price/volume data before adding more network traffic.


2.4 Separate raw observations from derived features
---------------------------------------------------

Example raw observation:

    BTCUSDT 5m candle
        Open
        High
        Low
        Close
        QuoteVolume
        CloseTime

Derived features:

    Return5m
    ATRP5m
    VolumeExpansion15m
    RelativeStrength4h
    CorrelationToBTC
    OIChange1h

Market-wide aggregates:

    Breadth4h
    MedianATRP5m
    ReturnDispersion4h
    MedianVolumeExpansion15m
    MedianCorrelationToBTC

Each layer should remain separately inspectable.


2.5 Deterministic behavior
--------------------------

All calculations should be deterministic.

Given the same raw input data, PTMagic should produce exactly the same feature values.

Avoid:
- Hidden adaptive behavior.
- Unlogged heuristics.
- Calculations that depend on wall-clock timing when exchange candle timestamps are available.
- Non-repeatable sampling.


2.6 Every feature should have explicit units
--------------------------------------------

Examples:

    Return4h                 percent
    ATRP5m                   percent
    Breadth4h                percent of eligible markets
    FundingRate              decimal or percent -- choose one standard
    VolumeExpansion15m       ratio
    CorrelationToBTC         -1.0 to +1.0
    BidAskSpreadPercent      percent
    OIChange1h               percent

Avoid ambiguous fields such as:

    Strength = 17.4

unless the meaning and range are defined.


======================================================================
3. TARGET DATA LAYERS [A PARTLY COMPLETE, B/C EXPANDING]
======================================================================

The target architecture should contain three major data layers.


3.1 Layer A: Raw market data

5. PHASE 1 - BASIC PRICE/VOLUME FEATURE FOUNDATION
    [1A PARTIAL, 1B DONE, 1C NEXT, 1D PLANNED, 1E PARTIAL]
======================================================================

Goal:
Extract substantially more information from basic OHLC/quote-volume data before adding futures-specific endpoints.


----------------------------------------------------------------------
5.1 Historical series cache
----------------------------------------------------------------------

PTMagic needs a reusable historical data cache. STATUS 2026-11-04: the 5m normalized rolling MarketDataStore/MarketDataService is implemented and incremental refresh works. This is an IN-MEMORY store; it does not survive process restart. Cold-start cross-section readiness remains a separate unresolved correctness issue.

Conceptual structure:

    MarketHistory
    {
        Symbol
        CandlesByInterval
    }

or a central store such as:

    MarketDataStore
        GetCandles(symbol, interval)
        GetLatestCandle(symbol, interval)
        GetTicker(symbol)

Important requirements:

- Candle data keyed by exchange timestamp.
- No duplicate candles.
- Closed and still-open candles distinguished.
- Configurable history length.
- Efficient rolling updates.
- Avoid redownloading full history every analyzer cycle.
- Thread-safe access if analyzer/network operations are concurrent.
- CancellationToken support.
- Clearly defined stale-data behavior.

Prefer maintaining one base timeframe where practical and aggregating locally where correct.

However, do not force local aggregation if Binance-provided timeframe candles are already efficiently available and preferable.


----------------------------------------------------------------------
5.2 Direction / returns
----------------------------------------------------------------------

Direction was historically available in legacy MarketTrendChange. STATUS: a separate reusable normalized per-asset return is now implemented at exact aligned closed-candle endpoints. Legacy calculation semantics remain untouched.

Per asset:

    Return5m
    Return15m
    Return1h
    Return2h
    Return4h
    Return8h
    Return12h
    Return24h

Definition:

    Return = (CurrentPrice / ReferencePrice - 1) * 100

The implementation must define:
- Whether CurrentPrice is the live price or most recent closed candle.
- How ReferencePrice is selected.
- What happens if exact interval boundaries do not align.
- How incomplete history is handled.

Recommended:
Use timestamp-aligned reference prices and preserve the existing PTMagic meaning where backwards compatibility matters.

Market-wide:
Calculate at least mean and median.

    MeanReturn4h
    MedianReturn4h

Median should be added because it is much less sensitive to a few extreme movers.

Potential additional aggregates:

    Top20MedianReturn4h
    Top50MedianReturn4h
    Top100MedianReturn4h


----------------------------------------------------------------------
5.3 Breadth
----------------------------------------------------------------------

STATUS: Basic return Breadth is implemented and runtime-tested as the metric named Breadth; strong/negative/indicator breadth remain optional extensions. Breadth denominators must be valid common-endpoint samples, with a separate readiness/coverage gate.

Breadth answers:

    How much of the market is participating in the move?

Initial breadth is simple return breadth.

Per timeframe:

    PositiveBreadth5m
    PositiveBreadth15m
    PositiveBreadth1h
    PositiveBreadth4h
    PositiveBreadth24h

Definition:

    number of eligible markets with return > 0
    ------------------------------------------------ * 100
                 eligible market count

Also useful:

    StrongPositiveBreadth
        % with return > configurable threshold

    NegativeBreadth
        % with return < 0

Example:

    MedianReturn4h = +2.0%
    PositiveBreadth4h = 82%

This means something materially different from:

    MedianReturn4h = +2.0%
    PositiveBreadth4h = 38%

Future optional breadth metrics:

    % above EMA50
    % above EMA200
    % positive MACD
    % with rising short-term trend

These should NOT be first-generation requirements because they add substantial indicator calculations.


----------------------------------------------------------------------
5.4 Dispersion
----------------------------------------------------------------------

STATUS: Dispersion is implemented and runtime-tested as population standard deviation of normalized return percentages. Median absolute deviation remains optional.

Dispersion measures how differently individual assets are moving.

Initial implementation:

    ReturnDispersion1h
    ReturnDispersion4h
    ReturnDispersion24h

First-generation calculation:

    standard deviation of per-asset returns

Because crypto has extreme outliers, later add a robust alternative:

    MedianAbsoluteDeviation

Possible output:

    ReturnStdDev4h
    ReturnMAD4h

Interpretation examples:

Broad coherent move:
    median return +2.0%
    breadth 80%
    dispersion low

Fragmented/speculative move:
    median return +2.0%
    breadth 52%
    dispersion very high

Dispersion should always be calculated over the exact same eligible universe as the accompanying breadth/return metric unless explicitly labeled otherwise.


----------------------------------------------------------------------
5.5 Volatility
----------------------------------------------------------------------

STATUS: PHASE 1C NEXT. Complete normalized OHLC is already retained, but ATRP, median ATRP and volatility breadth have NOT been implemented. Define the exact ATR convention and sampling interval before coding.

Use OHLC data to calculate actual short-term market volatility rather than inferring volatility from absolute return alone.

Primary first-generation metric:

    ATRP

ATRP:

    ATR / Price * 100

Per asset:

    ATRP5m
    ATRP15m
    ATRP1h

Use a clearly defined ATR period, initially 14 unless configuration requires otherwise.

Market-wide:

    MedianATRP5m
    MedianATRP15m
    MedianATRP1h

Add volatility breadth:

    % of markets with ATRP5m > X
    % of markets with ATRP1h > Y

Potential later additions:

    RealizedVolatility
    HighLowRangePercent
    BollingerBandWidth

Do not add multiple redundant volatility measures until ATRP behavior has been validated.


----------------------------------------------------------------------
5.6 Participation via recent quote-volume expansion
----------------------------------------------------------------------

STATUS: PHASE 1C NEXT. Quote volume is retained per normalized candle, but recent volume-expansion ratio/breadth are NOT implemented. Legacy 24h quote volume still supports rank/eligibility and the completed return-Concentration calculation.

Do NOT use raw 24h volume as the main participation metric.

24h quote volume remains useful for:
- Market ranking.
- Crude liquidity filtering.
- Universe selection.

Participation should instead measure whether recent trading activity is expanding or contracting relative to that asset's own recent normal level.

Per asset:

    VolumeExpansion5m
    VolumeExpansion15m
    VolumeExpansion1h

Example definition:

    CurrentIntervalQuoteVolume
    --------------------------
    AverageQuoteVolumeOfPreviousNComparableIntervals

Example:

    VolumeExpansion15m = 1.42

means current 15-minute quote volume is 42% above its recent average.

Important implementation choices:

- Prefer quote volume, not base volume, for cross-asset comparability.
- Do not compare partial current candles directly against full historical candles without normalizing for elapsed time.
- Easiest first-generation implementation:
  use the most recent CLOSED candle.
- If using live candles later:
  normalize expected volume by fraction of candle elapsed.

Suggested baseline periods:

    5m expansion:
        compare latest closed 5m candle to previous 12-24 candles

    15m expansion:
        compare latest closed 15m candle to previous 12-24 candles

    1h expansion:
        compare latest closed 1h candle to previous 12-24 candles

Market-wide:

    MedianVolumeExpansion15m
    VolumeExpansionBreadth15m
        % > 1.0

    StrongVolumeExpansionBreadth15m
        % > 1.5

This lets PTMagic distinguish:

    Price rising + participation expanding

from:

    Price rising + participation contracting


----------------------------------------------------------------------
5.7 Relative strength
----------------------------------------------------------------------

STATUS: RelativeStrengthMarket and RelativeStrengthBTC are implemented and runtime-tested using the shared normalized return series. They are per-asset metrics, with subtraction measured in percentage points.

No additional endpoint is required once per-asset returns exist.

Two forms should be calculated.


A. Relative strength versus market
----------------------------------

Example:

    SOLReturn4h = +6.2%
    MarketMedianReturn4h = +2.4%

    SOLRelativeStrengthMarket4h = +3.8 percentage points

Use subtraction rather than an arbitrary normalized score initially.


B. Relative strength versus BTC
-------------------------------

Example:

    SOLReturn4h - BTCReturn4h

Fields:

    RelativeStrengthMarket1h
    RelativeStrengthMarket4h
    RelativeStrengthMarket24h

    RelativeStrengthBTC1h
    RelativeStrengthBTC4h
    RelativeStrengthBTC24h

These are especially useful for SingleMarketSettings.


----------------------------------------------------------------------
5.8 Concentration
----------------------------------------------------------------------

STATUS: Return concentration IS implemented under the current canonical metric name Concentration, with Top10 ranked by trailing 24h quote volume. Volume concentration / percentage shares remain Phase 1C work. Do not conflate these two metrics.

Concentration answers:

    Is the market-wide reading broad, or dominated by a small number of assets?


A. Return concentration
-----------------------

Useful comparisons:

    Top10MeanReturn
    RemainingUniverseMeanReturn

or:

    Top10MedianReturn
    RemainingUniverseMedianReturn

Potential feature:

    Top10ReturnAdvantage4h

This helps identify BTC/large-cap-led markets versus broad participation.


B. Volume concentration
-----------------------

Using quote volume:

    BTCVolumeShare
    BTCETHVolumeShare
    Top5VolumeShare
    Top10VolumeShare

Definition:

    selected-group quote volume
    ---------------------------
    total eligible quote volume

These should be measured over a defined period, preferably recent volume rather than only 24h volume when feasible.


----------------------------------------------------------------------
5.9 Correlation / market cohesion
----------------------------------------------------------------------

STATUS: PHASE 1D PLANNED. The normalized store and common endpoint provide a foundation, but rolling synchronized return vectors and correlation calculations are NOT yet implemented.

Correlation should be calculated from synchronized return series, not raw prices.

Recommended first generation:

- Use 5m or 15m log/simple returns.
- Use a rolling sample window.
- Calculate per-asset correlation to BTC.

Per asset:

    CorrelationToBTC

Market-wide:

    MedianCorrelationToBTC
    MeanCorrelationToBTC

Later:

    AveragePairwiseCorrelation

Pairwise correlation is O(n^2), so it should not be the first implementation if Top100 is used frequently.

Correlation provides a measure of market cohesion.

High:
    Assets moving together.

Low:
    Rotational / fragmented market.

Negative:
    Unusual divergence requiring investigation.

12. CACHING AND NETWORK DESIGN [CORE IMPLEMENTED; STARTUP OPTIMIZATION OPEN]
======================================================================

CURRENT STATE: normalized 5m incremental refresh and zero-request current-cache raid were validated. A fresh PROCESS still reloads all normalized history and a long bootstrap can cross candle boundaries, creating the Phase 1A completeness issue. Legacy history recreation remains separate.

The expanded analyzer must not turn every PTMagic cycle into a full historical redownload.


12.1 Cache by data type
-----------------------

Different data has different natural refresh intervals.

Examples:

Live ticker:
    seconds to analyzer-cycle frequency

Closed klines:
    update when a new candle closes

Funding:
    much slower-changing

OI:
    moderate interval

Long/short ratios:
    according to Binance supported sampling intervals

Order book:
    high frequency only if Phase 5 is enabled


12.2 Incremental history updates
--------------------------------

On startup:

    Load sufficient bootstrap history.

Afterward:

    Request only missing/new data.

Avoid:

    Download last 500 candles for Top100
    every analyzer cycle.


12.3 Per-endpoint refresh policy
--------------------------------

Create explicit policies such as:

    Klines5mRefresh
    Klines15mRefresh
    OpenInterestRefresh
    FundingRefresh
    PositioningRefresh
    TakerFlowRefresh

Do not let each feature independently decide to make network calls.


12.4 Central request scheduling
-------------------------------

Prefer:

    Analyzer
       asks MarketDataService for snapshot

MarketDataService:
       decides what must be refreshed

instead of:

    Breadth calculator -> Binance
    ATR calculator -> Binance
    Volume calculator -> Binance
    Correlation calculator -> Binance

The latter produces redundant requests and makes rate-limit behavior difficult to control.


12.5 Rate limits
----------------

Track Binance request weights centrally where applicable.

Required behavior:

    bounded concurrency
    cancellation
    timeout
    retry only when appropriate
    exponential backoff/jitter where appropriate
    rate-limit awareness
    clear warning logs

Never let an optional analytics endpoint prevent core PTMagic operation.


12.6 Partial data failure
-------------------------

If one endpoint fails:

    Preserve valid core analysis.
    Mark affected features unavailable/stale.
    Do not substitute zero.

Zero is often a valid market value and must never mean "missing."

Use nullable values/status metadata such as:

    Value
    Timestamp
    IsStale
    IsAvailable

24. IMPORTANT DESIGN DECISIONS ALREADY MADE [CURRENT AND REAFFIRMED]
======================================================================

These should be treated as current project guidance unless explicitly reconsidered.

1. Expand PTMagic's own deterministic analysis first.

2. Do not add an external AI/LLM layer as part of this roadmap.

3. Do not let new analytics bypass PTMagic's existing GlobalSettings /
   SingleMarketSettings architecture.

4. Do not initially change ProfitTrailer's actual technical entry logic.

5. The first development step is NOT adding every Binance endpoint.
   First determine what can be derived from data PTMagic already downloads.

6. Breadth is high priority because it adds information that a simple market
   average loses.

7. Dispersion is high priority because it is almost free once returns exist.

8. ATRP is the preferred initial volatility measurement.

9. Participation should be measured primarily using RECENT QUOTE-VOLUME
   EXPANSION, not raw 24-hour volume.

10. Relative strength and concentration should be derived locally from the
    same price data.

11. Correlation should use synchronized return series, not raw prices.

12. Futures derivatives/positioning/flow endpoints come after the first
    price/volume-derived generation is stable.

13. Liquidity/order-book analysis comes later because it has materially higher
    data-collection cost.

14. Missing data must never silently become zero.

15. All new features must be independently inspectable and testable.

16. New analytics should initially run in observation mode/TestMode before
    they are permitted to modify ProfitTrailer behavior. First-generation
    trigger wiring is complete, but live changes remain out of diagnostic scope.

17. The analyzed market universe must be explicit and consistent across
    measurements.

18. Market/underlying-type filtering should be centralized so crypto-only
    breadth can exclude TradFi-linked or other non-crypto instruments when
    desired.

19. Binance networking code should return raw data; PTMagic analysis classes
    should perform calculations.

20. Data collection should be cached and incremental rather than repeatedly
    downloading full history.

25. CONTEXT FOR FUTURE DEVELOPMENT CONVERSATIONS [CURRENT HANDOFF]
======================================================================

When this document is pasted into a future conversation, assume the following
project intent:

Building on the COMPLETED PTMagic 2.9 modernization and optimization release,
PTMagic 2.10 expands the deterministic market-analysis engine for Binance Futures.

The objective is NOT to create another entry-strategy engine.

ProfitTrailer already contains the technical strategy that decides actual
entries/exits.

PTMagic's expanded responsibility should be to understand the broader market
and each market's context more accurately, then use that information to make
better decisions through its existing configuration mechanisms.

Examples of decisions PTMagic may eventually make using these features:

    How many markets should be eligible to trade?
    Which market groups should be disabled?
    Should allocation be reduced?
    Is the market move broad or narrow?
    Is volatility abnormally high or low?
    Is current participation confirming price movement?
    Is a symbol materially stronger/weaker than the broader market?
    Is the market tightly correlated or rotational?
    Is leverage expanding?
    Is positioning crowded?
    Is aggressive flow confirming or contradicting price?
    Is liquidity poor enough that an asset should be excluded?

The development order should favor:

    Reuse existing raw data
        ->
    derive cheap deterministic features
        ->
    validate
        ->
    add futures-specific raw data
        ->
    derive futures structure
        ->
    integrate with GlobalSettings/SMS
        ->
    add expensive liquidity analysis later

as PTMagic 2.10; read Part I above, verify repository HEAD, review applicable

Phase 1A readiness before Phase 1C.
